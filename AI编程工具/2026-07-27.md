### 1. JetBrains Context 正式发布 — 代码库智能层 ⭐️⭐️

| 项目 | 内容 |
|------|------|
| **来源** | JetBrains AI Blog（2026-07-22 前后） |
| **PM技能** | product-strategy, competitive-brief |

JetBrains 正式推出 **JetBrains Context**，一个面向编码 Agent 的代码库智能层（Repository Intelligence Layer），作为 JetBrains AI for Teams and Organizations 的一部分，对 JetBrains AI 订阅用户免费提供。

**核心机制：**
- 增量构建代码库语义索引
- 提供语义检索能力，Agent 无需反复搜索和读取文件即可获取相关上下文
- 两个核心组件：后端索引引擎 + 多编辑器插件

**支持覆盖：**
- **Agent:** Claude Code、Codex CLI、JetBrains Junie CLI
- **编辑器:** JetBrains IDE、JetBrains Air、VS Code、其他支持编辑器
- **语言:** 首批支持主流后端语言，更多语言陆续加入

**解决的核心问题：**
JetBrains 首席技术官 Vlad Tankov："我们花了几十年帮开发者在复杂代码库中快速上手。事实证明，AI Agent 在不熟悉的项目中也需要同样的帮助。"
- Agent 大部分时间花在搜索代码、启动探索子Agent、读取文件——消耗 token 和时间
- 即使最强大的模型，上下文窗口和代码库可见性有限也可能导致 Agent 找错代码
- JetBrains Context 让 Agent 花更少时间探索，更多时间完成任务

**🫘 分析：** 这是代码库索引（Codebase Indexing）赛道的一个重要产品化里程碑。与 Cursor 的代码库索引和 GitHub Copilot 的 `@workspace` 不同，JetBrains Context 是**跨 Agent、跨编辑器**的独立基础设施层——不绑定到特定 Agent 或 IDE。这与 JetBrains 的"零厂商锁定"策略一致。在 JetBrains 2026.2 系列产品（Rider、ReSharper、WebStorm、RubyMine）中，Context 与 Agent Skills Manager 一起构成了面向 AI 编程时代的完整"IDE 智能层"。

### 2. MCP 2026-07-28 正式发布倒计时 24 小时 ⏰🔥

| 项目 | 内容 |
|------|------|
| **来源** | MCP 官方博客 / TechTimes / WorkOS / byteiota / Microsoft / Stacktree（综合） |
| **PM技能** | product-strategy |

MCP 2026-07-28 规范将于明天正式发布。这是 MCP 自发布以来最大的一次修订。

**核心变化详解（与 07-26 报告的补充）：**

**a) 无状态协议 — 架构级变革**

| 删除 | 新增 |
|------|------|
| `initialize`/`initialized` 握手（SEP-2575） | 协议版本/客户端信息/能力在 `_meta` 中随每个请求传输 |
| `Mcp-Session-Id` 标头及协议级会话（SEP-2567） | `server/discover` 方法按需获取服务器能力 |
| 粘性路由 / 共享 Redis 会话存储需求 | 任何实例处理任何请求，普通轮询负载均衡即可 |

**b) 路由与可观测性**

| 新增 | 说明 |
|------|------|
| `Mcp-Method` / `Mcp-Name` HTTP 头 | 网关无需解析 JSON body 即可路由和限流 |
| `ttlMs` / `cacheScope` | `tools/list`、`resources/list` 等列表响应可缓存 |
| W3C Trace Context (`traceparent`, `tracestate`) | OpenTelemetry 链路追踪内建支持 |

**c) 扩展机制正式化**

| 扩展 | 说明 |
|------|------|
| **Tasks** 🔥 | 从实验性毕业。`tools/call` 返回 task handle → `tasks/get`/`tasks/update`/`tasks/cancel`。支持超长 Agent 工作流 |
| **MCP Apps** | 服务器可渲染 HTML UI 到沙箱 iframe，通过 JSON-RPC 回传通道交互 |
| Multi Round-Trip Requests | `InputRequiredResult` 替代 SSE 流，服务器中断请求等用户输入后重新发起 |

**d) 废弃清单（12 个月窗口）**

| 废弃项 | 替代方案 |
|------|------|
| Roots | 直接通过工具参数或 resource URI 传递范围 |
| Sampling | 直接 LLM API 调用 |
| Logging | stderr（stdio 传输）或 OpenTelemetry（结构化日志） |

**e) 授权升级**

- MCP 服务器正式成为 **OAuth 2.1 资源服务器**
- 必须实现 OAuth 2.0 Protected Resource Metadata（RFC 9728）
- 客户端必须实现 Resource Indicators（RFC 8707），防止恶意服务器获取其他服务器的 token

**f) 错误码变化**

| 旧 | 新 | 说明 |
|------|------|------|
| `-32002`（MCP自定义） | `-32602`（JSON-RPC Invalid Params） | 缺失资源错误——任何硬编码 `-32002` 的客户端需更新 |

**SDK 就绪状态：**
- Python v2、TypeScript v2、Go v1.7.0-pre.1、C# v2.0.0-preview.1 — beta 已发布
- GitHub MCP Server 已提前适配（移除 Redis 会话、升级 elicitation、避免深层报文检查）

**🫘 分析：** MCP 1.0 对 AI 编程工具的影响是结构性的：
1. **Claude Code 的 MCP 生态将首先受益** — Anthropic 是 MCP 的创建者，Claude Code 已有最丰富的 MCP 服务器生态
2. **Codex CLI / Cursor / GitHub Copilot** — 都需要适配新规范，GitHub 已经先行
3. **无状态化是基础设施福音** — MCP 服务器从"奇怪的带状态雪flake"变成"普通 HTTP 服务"，可用标准云基础设施部署
4. **Tasks 扩展是 Agent 编码的核心使能器** — 长周期 Agent 任务（重构、大规模代码生成）现在有正式协议支持
5. **MCP Apps 开辟新可能性** — Agent 工具现在可以带交互式 UI，超越纯文本/JSON 交互

**最常⻅漏洞分布：**

| 漏洞类型 | 数量 | 说明 |
|------|:---:|------|

### 2. "如何停止 Vibe Coding？"争议持续

| 项目 | 内容 |
|------|------|
| **来源** | Alex Klos 博客（2026-07-24） |
| **PM技能** | product-strategy |

Alex Klos 发表长文"How Do We Stop Vibe Coding?"，呼应了 Andrej Karpathy（3 月播客中承认"从 12 月以来可能没写一行代码"）和 Grady Booch（称当前为"软件工程第三个黄金时代"）：

**核心论点：**
- Vibe coding 的两个根本问题：(a) 损害对代码库的个人理解，(b) 自然语言→代码的信息损失导致不可靠输出
- 我们正处于"vibe coding 赌场"——所有人都在疯狂生成代码，"拉下拉杆，祈祷最好结果"
- 工具的演进方向应该是"从意图直接生成代码"（类比编译器抽象了机器，Agent 抽象了代码），但当前缺少意图→代码之间的质量保证层

**提出的解决方案（不成熟阶段）：**
- Markdown Spec 驱动开发
- Skills（Claude Code 的 Skills 机制）
- Spec Kit / OpenSpec
- Kiro（意图驱动的 AI 编程工具）
- 测试驱动开发 + AI 代码审查结合

**与已有报告对比：** 07-26 报告已覆盖 Vibe Coding vs Vibe Engineering 概念分化，本期是另一位开发者的深度批判和解决方案探索。两者互补。

### 1. Jensen Huang 联合 24 家科技巨头反对开源 AI 限制 🔥🔥

| 项目 | 内容 |
|------|------|
| **来源** | Glitchwire / NYT / en.sedaily（2026-07-27） |
| **PM技能** | porters-five-forces |

在 K3 权重开源的同日，Glitchwire 报道 **Jensen Huang 和 24 家科技巨头**联合反对美国政府对开放权重 AI 模型的潜在限制。

**美国内部立场分裂：**

| 阵营 | 立场 | 理由 |
|------|------|------|
| **Nvidia、Microsoft** | 支持允许中国开源 AI | 促进市场竞争和技术创新；开源生态利好芯片和云需求 |
| **OpenAI、Anthropic** | 要求加强监管 | 开源模型鼓励知识产权侵权，可能导致黑客滥用和国家安全威胁 |
| **White House** | 指控 Moonshot 使用被禁运芯片和"蒸馏"技术 | 国家安全角度 |

**Nvidia/Microsoft 的逻辑链：** 更多开源模型 → 更多部署需求 → 更多 GPU 芯片销售（Nvidia）和云服务需求（Microsoft Azure）→ 产业整体发展。这是一个自洽的商业逻辑——与其限制对手，不如用更大的市场来摊薄竞争压力。

**OpenAI/Anthropic 的逻辑链：** 中国开源模型冲击定价 → 闭源模型的利润率受威胁 → 研发投入可持续性受质疑 → 需要政策保护。

**🫘 分析：** 这不只是中美技术竞争，而是美国内部的**两种 AI 商业模式之战**——"基础设施层获利"（Nvidia/MS）vs "模型层获利"（OpenAI/Anthropic）。对编程工具的影响：如果美国政府限制开源 AI，Cursor/Continue 等支持多模型的工具可能失去集成中国开源模型的选项；如果不限制，K3 等模型将加速编程工具的"模型民主化"。

| PM技能 | porters-five-forces |

**与已有报告对比：** 全新内容。此前 07-24 报告覆盖了中国芯片政治压力，本期是美国内部对开源 AI 的分裂。
